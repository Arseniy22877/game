# AGENTS.md

Инструкции для ИИ-агентов (Codex, Claude Code и т.п.) и людей, работающих в этом репозитории.
Claude Code читает этот файл через `CLAUDE.md`.

## Проект

Образовательная бизнес-игра для курса «Мастерская по созданию игр» (Центральный Университет).
Формат как у Jackbox: преподаватель ведёт игру со своей страницы, команды студентов подключаются со своих устройств через браузер.

Каждый раунд команда:
- распределяет бюджет по сферам (настраиваемые атрибуты);
- выбирает стратегии;
- покупает исследования за очки QP (в движке это `Hints`);
- пишет отчёт из 4 вопросов (`DecisionData`).

Когда все команды отправили решения, преподаватель завершает раунд и видит для каждой команды возможные события с вероятностями. Он вручную выбирает, какие события произойдут (выбор может быть пустым). После этого состояние игр обновляется и начинается следующий раунд.

## Команда и зоны ответственности

| Зона | Папки | Владелец |
|------|-------|----------|
| Движок | `gameengine/`, формат `scenarios/*.json` | автор движка |
| Бэкенд | `cmd/`, `internal/`, `migrations/` | бэкендер |
| Фронтенд | `web/` | фронтендер |
| Контракт фронт↔бэк | `docs/api.md` (+ DTO в `internal/api`) | бэк + фронт вместе |

**Правило:** не меняй файлы чужой зоны без согласования с её владельцем. Если для твоей задачи нужно изменение в чужой зоне, опиши его (issue или сообщение команде) и не правь сам.
Бэкенд использует движок только как библиотеку. Все вызовы `gameengine` собраны в одном пакете `internal/enginebridge`.

## Архитектура бэкенда (согласовано)

- **Один Go-процесс.** Движок подключён как пакет, без микросервисов, Redis и брокеров.
- **Одна активная игра в каждый момент времени.** Параллельные сессии не нужны. Прошлые игры остаются в БД как история.
- **REST для команд** (регистрация, готовность, старт, решения, завершение раунда, выбор событий, оценки).
- **WebSocket только от сервера к клиенту.** Сообщения вида `{ "type": "...", "payload": {...} }`. После переподключения клиент делает `GET` полного состояния и снова слушает WS.
- **Авторизация через токены.** Команда получает токен при регистрации. Токен преподавателя задаётся в env `ADMIN_TOKEN` на сервере.
- **SQLite** (`modernc.org/sqlite`, чистый Go без CGO, режим WAL).
- **Состояние игры живёт в памяти, БД служит журналом.** Каждое действие сначала пишется в БД, потом отправляется ответ. События всегда передаются в движок явно через `FireEvents(ids)`, никогда через `FireEvents(nil)`. Благодаря этому игру можно восстановить, заново прогнав решения из БД.
- **В БД сохраняем:** игры (сессии), команды и участников, решения по раундам, прогнозы событий, выбранные события, снапшоты состояния (DTO, а не сырой `GameState`), оценки.
- **Оценки преподаватель ставит один раз за всю игру** по каждому ключевому атрибуту, а не за каждый раунд.
- **Решение команды передаётся в движок сразу при отправке** (`PassAttributes` / `PassStrategies` / `PassHints`), чтобы команда сразу видела ошибку валидации. Стоимость решения (деньги и QP) бэк проверяет заранее сам, потому что движок ловит нехватку бюджета только в `CalculateState`. `CalculateState` и `GetPredicts` вызываются, когда преподаватель нажимает «Завершить раунд».
- **Деплой:** VPS, Linux-бинарник + systemd. Перед бэком стоит Caddy (автоматический HTTPS, `wss://`).

Планируемая структура:

```
cmd/server/          точка входа
internal/api/        HTTP-хендлеры, DTO
internal/ws/         WebSocket-хаб
internal/game/       конечный автомат игры: Lobby → RoundOpen → RoundClosed → … → Finished
internal/enginebridge/  единственное место, которое вызывает gameengine
internal/store/      SQLite
migrations/          SQL-миграции (embed)
gameengine/          движок
scenarios/           JSON-сценарии (id сценария = имя файла без .json)
web/                 фронтенд
```

## Движок: что важно знать

API находится в `gameengine/api.go`:
- `LoadGames()` загружает сценарии из `scenarios/*.json`.
- `GetGameInstance(id)` создаёт новое `GameState`.
- Ход раунда: `Pass*` → `CalculateState()` → `GetPredicts()` → `FireEvents(ids)`.

Особенности, которые нужно учитывать:
- У `GameState` нет мьютекса. Доступ к нему синхронизирует вызывающий код.
- `GameState` и `ProbResult` содержат указатели на данные сценария. Не сериализуй их напрямую: используй DTO.
- Поле `Iteration` движок не увеличивает. Номер раунда ведёт бэк.

## Задачи и доска

Задачи — GitHub Issues этого репо, доска — https://github.com/users/Warl0rdd/projects/3 (поля `Status`: Todo / In Progress / Done и `Зона`: Бэк / Фронт / Движок / Контракт / Общее). Лейблы зон: `area:backend`, `area:frontend`, `area:engine`, `area:contract`.

Чтобы агенты не брали одну задачу дважды:
1. **Перед началом работы** проверь issue: если у неё уже есть исполнитель или статус In Progress, не бери её.
2. **Взял задачу:** `gh issue edit <N> --add-assignee @me`, переведи её в In Progress на доске и только потом начинай работу.
3. **Нет подходящей issue:** сначала создай её (`gh issue create` с лейблом зоны), потом работай.
4. **В PR пиши `Closes #N`.** После мержа задачу переводи в Done.

Как поменять статус через CLI (нужен scope `project`: `gh auth refresh -s project`):
```sh
gh project item-list 3 --owner Warl0rdd --format json   # найти id элемента
gh project item-edit --project-id PVT_kwHOA-85Uc4Brgug --id <item-id> \
  --field-id PVTSSF_lAHOA-85Uc4BrgugzhpzIws --single-select-option-id <option>
# Status: Todo=f75ad846, In Progress=47fc9ee4, Done=98236657
```

## Рабочий процесс

- **Не пушим напрямую в `main`.** Работаем в ветке (`feat/...`, `fix/...`, `chore/...`) и открываем PR через `gh pr create`.
- **Изменение контракта (API, WS-сообщения, DTO) делается отдельным PR,** и об этом сообщают команде.
- **Перед PR прогоняем:** `gofmt -l .` (вывод должен быть пустым), `go vet ./...`, `go test ./...`.
- **Не коммитим** бинарники, файлы БД, `.env` и секреты.

## Команды

```sh
go test ./...        # все тесты
go vet ./...
go run ./cmd/server  # запуск сервера (когда появится)
```
